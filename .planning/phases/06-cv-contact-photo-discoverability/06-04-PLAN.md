The email. React SSR escapes `&` in both text nodes **and** attribute values — measured across four
variants — so `<span>{"a&#64;b"}</span>` ships as `a&amp;#64;b` and the obfuscation becomes worse
than useless. JSX also decodes literal entities in source at compile time, so writing `&#64;`
directly gives a plain `@`. Both paths fail and neither fails loudly. `dangerouslySetInnerHTML` is
the only route to entities in the emitted bytes.

Confine it to one small component in this file. Encode `@` as `&#64;` and `.` as `&#46;` in both
the `mailto:` href and the link text, and emit a single anchor carrying `link-quiet`. The browser
decodes at parse time, so the href resolves to a real `mailto:` and `textContent` equals the real
address — which is what makes it keyboard-reachable, screen-reader-readable, and selectable, the
three things `[at]`/`[dot]` plain text cannot all deliver.

Write the safety argument in a comment directly above it, because it must not read as carelessness:
the encoded string is derived from a module constant in our own source, this site has no user input
of any kind anywhere, and the pattern must never spread beyond this one component. State that the
goal is deterring cheap regex harvesting, not cryptographic protection — a determined scraper gets
any address a human can reach, and that is explicitly accepted.

Render nothing for the email when `EMAIL` is null. The component must be exercisable with the
address passed in, so plan 06-09's Playwright spec can prove the three-part accessibility test
against a real value rather than only against absence.
